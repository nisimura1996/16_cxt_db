## 1\. ローカルデータ（MySQL等）の保管が必要な理由

APIから都度直接取得して表示するのではなく、ローカル（自前DB）に保管すべき理由は以下の4点。

- **APIのリクエスト制限（Rate Limit）と表示速度の担保** ユーザーや検索エンジンのクローラーがページにアクセスするたびにAPIを叩くと、一瞬で呼び出し上限に達してエラーになる。また、APIレスポンス待ちによる表示速度低下（SEO上のマイナス）を防ぐため。
- **AI APIの重複課金防止** AIで生成したテキストコンテンツをDBに保存しておかないと、ページ表示のたびにAI APIのコストが発生する。
- **絞り込み・検索・ピラー構造の実現** 「地域×予算」「カテゴリ×特徴」などの複数条件によるフィルタリングや一覧ページの生成は、自前DBにデータがインデックス化されていないと高速に処理できない。
- **URLとページの永続化（SEO対策）** 検索エンジンにインデックスさせるためには、固定されたURLと静的なHTML構造が不可欠。

## 2\. MySQLのデータを基にしたAIコンテンツ生成の流れ

「APIデータ取得 → MySQL保存 → AIによるコンテンツ生成 → DB更新・ページ公開」というパイプラインが標準的な構成となる。

```
[外部API]
   │ (定期取得スクリプト: Python / PHP等)
   ▼
[MySQL: 生データテーブル]
   │ (未処理レコードを抽出)
   ▼
[AI API (Gemini等)] ─── プロンプト: 生データ(スペック/特徴)を渡し、解説文・要約・比較を生成
   │ (生成テキスト)
   ▼
[MySQL: 記事データ / WordPress]
   │ (カスタムフィールド / 投稿本文へ格納)
   ▼
[Webサイト (ピラー / クラスターページ)]
```

### 生成のポイント

- **スペック表などの事実データ**: APIから取得した正確な値をそのままHTML/テーブルとして出力（AIを通さないことでハルシネーションを防止）。
- **リード文・特徴まとめ・おすすめの理由**: MySQLから渡したパラメータ（カテゴリ、価格帯、機能群）をAIプロンプトに変数値として埋め込み、ユニークな解説文を生成。

## 3\. 運用上の重要注意点

- **API側のキャッシュ規約**
	- **Amazon PA-API**: 価格や在庫情報のローカル保持は原則24時間以内。表示時に最新価格を再取得するか、定期バッチで更新が必要。
		- **楽天API等**: キャッシュ期間や利用規約上の「データ保持ルール」を事前に確認すること。
- **重複コンテンツ（低品質判定）の回避** AI生成テキストが全ページで似通ったテンプレート構文になるとGoogleの低品質ペナルティを受ける。DB内の属性データ（価格帯、ターゲット層、利用シーンなど）ごとにプロンプトのトーンや比較軸を分岐させることが必須。

**Gemini**

結論から言えば、WordPressのサーバー（MySQLデータベース）上のカスタムフィールドや投稿本文にすべてのデータが登録・保存された後であれば、サイトの表示や独立稼働においてPC上のローカルJSONファイルは不要となるため、削除しても問題ない。

ただし、提示された現在のワークフローを考慮すると、ローカルファイルを削除することで以下の影響と対応が必要になる。

### 1\. ピラーページ生成スクリプトの改修が必要になる

現在、ピラーページを作成する際「ローカルのJSONファイルから商品情報をマージし、AIで再生成している」フローであるため、ローカルファイルを都度削除してしまうとこの処理が動かなくなる。 ローカルファイルを削除する運用にする場合は、ピラーページ生成スクリプトの処理を「WordPressのREST API（GETリクエスト）を叩き、登録済みのカスタムフィールドから対象商品のデータを取得してAIに渡す」という仕様に変更する必要がある。

### 2\. 一括再生成（バッチ処理）時のオーバーヘッド

将来的に「AIのプロンプトを改良したので、過去の商品レビューを一括で生成し直したい」となった場合、データがローカル（JSON）にあれば即座にPython等でループ処理を回せるが、サーバーのみにデータがある場合は、全件REST APIで取得（GET）し、再生成後に更新（POST/PUT）する通信のオーバーヘッドが発生する。

### 3\. 今後の運用設計の選択肢

**パターンA：データベース完全正本化（ローカルファイル削除）** WordPressを唯一のデータソース（マスター）とする。投稿完了後にローカルJSONは削除（または一時ファイルとして揮発）。ピラーページ生成やデータ修正時は、常にREST APIでWordPressから最新データを引っ張ってくる構造にする。PCのストレージは最もクリーンになる。

**パターンB：処理済みアーカイブ化（推奨）** テキストデータであるJSONは容量が非常に軽微であるため、削除はせず、Pythonスクリプト側で「WordPressへのPOST投稿が成功(ステータス200/201)したら、対象のJSONファイルを `processed` や `archive` ディレクトリへ自動移動（またはZIP圧縮）する」処理を追加する。 これにより、作業ディレクトリを綺麗に保ちつつ、既存のピラーページ生成スクリプトを改修せずにそのまま流用でき、万が一のサイトデータ消失時の復元用生データとしても機能する。
